# DECISIONS.md

1. **Indexes.** I created three indexes:
   - **`ux_emp_code`** — unique index on `employees.emp_code`. Enforces uniqueness at the database level so two concurrent `POST /employees` with the same code cannot both succeed (one gets `DuplicateKeyError` → 409). Also speeds up every employee lookup by `emp_code`.
   - **`ux_empcode_date`** — unique compound index on `attendance_logs.(emp_code, date)`. Enforces the one-record-per-day invariant atomically, so concurrent punch-ins for the same employee and date produce exactly one 201. Also serves the `GET /attendance` filter on `emp_code` and the analytics aggregations that match on `emp_code + date range`.
   - **`ix_date_desc_emp_asc`** — non-unique compound index on `attendance_logs.(date DESC, emp_code ASC)`. Covers the `GET /attendance` default sort order (`date` descending, `emp_code` ascending) and the date-range filters used by every analytics endpoint, letting MongoDB do indexed sorts and range scans instead of in-memory sorts.
   - **`ix_department`** — non-unique index on `employees.department` for the department-filtered queries in the summary and trend endpoints.
   I considered a compound index on `(emp_code, punch_in)` for the punch-out lookup but rejected it: punch-out queries are point lookups (one `emp_code`, sorted by `punch_in` descending) and the existing unique index on `(emp_code, date)` already provides the `emp_code` prefix. A dedicated index would add write overhead for minimal read benefit.

2. **Punch-in race.** Two identical punch-in requests arrive at the same instant. Both compute the same `emp_code + date` key. Both attempt `insert_one`. The unique compound index `ux_empcode_date` guarantees that exactly one insert succeeds. The other raises `DuplicateKeyError`, which my code catches and returns 409. There is no check-then-insert race because the uniqueness enforcement is inside MongoDB's storage engine, not in application code.

3. **Ties.** The leaderboard uses MongoDB's `$setWindowFields` with `$rank` (standard competition ranking). If two employees are tied on `total_late_minutes` at the cutoff of `limit`, they share the same rank and `$rank` skips the next number (e.g., 1, 2, 2, 4). My filter is `rank <= limit`, so **both** tied employees are included. The response can therefore contain more than `limit` rows when ties occur at the boundary. Within a rank, rows are ordered by `emp_code` ascending for determinism.

4. **Headcount.** The department summary starts from the `employees` collection, not from `attendance_logs`. I first aggregate all employees whose `joined_on <= last_day_of_month` grouped by department. This gives the headcount directly from employee records, so people with zero attendance logs are still counted. Attendance stats are then computed separately and merged by department name. A department where headcount is 0 (no employees joined by month-end) is omitted entirely.

5. **One thing I would change.** At 100× the data (~10M attendance records) I would switch the analytics endpoints to **pre-computed materialized views** (or MongoDB's `$merge`-based incremental aggregation). Right now every analytics request runs a full aggregation over the month's records on the fly. At scale, I'd run a nightly (or event-driven) job that aggregates daily/monthly rollups into a `stats` collection — one document per employee-month and one per department-month. The API would read these pre-aggregated documents in O(1) instead of scanning millions of records. The trade-off is slight staleness (acceptable for dashboards) and added complexity in the write path to keep rollups in sync.
